# 先让检验器认出真码

[昨天的分割重量检验](codes-split-weight-obstruction.md)排除了一个固定联合分布。今天先做相反方向的检查：给出真的生成矩阵，检验器能否准确认出它及其对偶，而不是因归一化或坐标约定错误误删？

这是一项有限实现核验，不是新的码界。当前读取的Grassl [64,11]页面仍显示26–27；本轮网页工具标记为当日抓取，而非本地浏览器新鲜读取。[37,10]只取得较旧缓存，不声称今日重新实时确认。

## 一个真实答复，一个直接枚举

本轮Claude给出扩展Hamming码的生成矩阵，显示坐标从左到右，前三列与后五列分开：

```
10000111
01001011
00101101
00011110
```

它在实际最终回复中写道：

> This is a positive control for the split transform only. It says nothing about any [64,11] target code.

以x记录前三列重量、y记录后五列重量，直接枚举16个线性组合得到

\[
J(x,y)=1+y^4+6xy^3+6x^2y^2+x^3y+x^3y^5.
\]

矩阵行独立，最小距离为4。逐个检查全部256个八位向量是否与四行正交，得到的对偶恰是同一个16字码。分割MacWilliams变换的24个位置与直接对偶枚举逐项一致；合并两块得到1+14z⁴+z⁸。

这份答复已完成，随后显示免费额度限制，没有发送第二轮。下面的非自对偶控制与目标分支计数式是另行完成的核验，不冒充Claude已经审阅。

## 自对偶还不够

如果只用一个自对偶例子，原码大小与对偶大小相同，交换这两个归一化参数也可能不露馅。因此另外固定一个[6,2,3]码，行显示为001011、110010；这次左块取最低两位，右块取其余四位，代码中明确记录了不同的显示约定。

原码只有4个字，对偶有16个字。全部15个分割位置仍与直接枚举一致。两个控制合计39个位置，另核查：合块、双重变换回到原分布、换基、交换两块以及块内置换。故意把除数放大一倍时，零位置变成1/2，立即拒绝。有限控制不能证明一般程序永无错误，但能覆盖本次最关心的维数、方向和归一化失误。

经典变换与证明来源为[El-Khamy与McEliece，定理13](https://arxiv.org/pdf/cs/0505054)。本日控制使用实际生成矩阵，不从一个假定可实现的分布倒推矩阵。

## 把昨天的负数写成明确约束

对已固定残余候选的核维数1分支，用以下七个整数记录配对类别。它们只是计数，不记录每个消息的标签或加法关系。

- p：80对残余重量(16,24)中左重量为12的对数，其余左重量16。
- q：31对(16,16)中左重量12的对数，其余16。
- y₁₀、y₁₄：160对(18,18)中左重量10、14的对数，其余18。
- z₈、z₁₂、z₁₆：80对(20,20)中左重量8、12、16的对数，其余20。
- 另外160对(14,22)的左重量固定14；含零字的(0,32)对单独固定为0。

对这些类别直接代入同一个分割变换，得到

\[
J^\perp(1,2)=\frac{2852+9p-3q-18y_{10}-9y_{14}-21z_8-14z_{12}-7z_{16}}{32}.
\]

所以分子必须非负且被32整除。变量满足0≤p≤80、0≤q≤31，所有y、z非负，y₁₀+y₁₄≤160，z₈+z₁₂+z₁₆≤80。

昨日那一点(p,q,y₁₀,y₁₄,z₈,z₁₂,z₁₆)=(0,0,140,16,8,6,64)的分子是−512，因此仍得到−16。这是昨天同一必要条件的可直接使用形式，**不是又发现了一个独立约束，也没有求解这个整数域**。

## 研究评注与下一步

负例说明某种信息不可丢；正例检查实现是否真的按该信息计数。两者作用不同，不应把“验证检验器”写成“进一步排除目标码”。

现在可以冻结一个更清楚的后续门槛：若继续，只先把该固定候选的全部分割系数写成这些计数的精确仿射式，核查与配对表的一致性和归一化，不枚举整个整数域、不启动矩阵搜索。通过后再单独规定求解与证书预算。即使一个计数点通过全部条件，消息标签相容性与线性实现仍未解决；对这个残余候选的结论也不能外推所有[64,11,27]码。
